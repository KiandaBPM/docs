REST APIs

  • 1: Authentication
  • 2: Instances
  • 3: Summaries API

Kianda’s REST Application Programming Interface (API) can be used to perform operations or methods such as create, update and get/retrieve items on a number of key areas that include:

  • Processes - namely process designs created by administrators or designers in Kianda Designer
  • Instances - namely instances of processes or records created by form users who have saved or submitted details in a process instance
  • Tasks - namely scheduled tasks created by administrators or instigated by processes, as seen in the Scheduled tasks function within Administration

The following pages introduce APIs for the above. In all cases Authentication is required for requests.

1 - Authentication

Kianda REST APIs use OAuth 2.0 bearer tokens. Requests run with the authenticated user’s permissions, so the user must have access to the data and operations your integration requires.

Use your workspace’s HTTPS URL for token and API requests.

Request an access token

The request below uses Kianda’s existing password-grant interface.

OAuth security guidance: RFC 9700, section 2.4 states that the resource owner password credentials grant must not be used. The example below documents Kianda’s existing interface.

POST https://{workspace-domain}/token
Content-Type: application/x-www-form-urlencoded

Send these parameters in the form-encoded request body:

ParameterValue
grant_typepassword
usernameThe Kianda user’s username.
passwordThe Kianda user’s password.
scopeThe target workspace’s subscription ID.

For this request, scope identifies the Kianda subscription. Find it under Administration > Subscription > Subscription Details > Subscription Id.

The following example reads credentials and the subscription ID from environment variables. Set KIANDA_USERNAME, KIANDA_PASSWORD, and KIANDA_SUBSCRIPTION_ID, and replace the workspace URL before running it.

curl --request POST \
  'https://your-workspace.kianda.com/token' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=password' \
  --data-urlencode "username=$KIANDA_USERNAME" \
  --data-urlencode "password=$KIANDA_PASSWORD" \
  --data-urlencode "scope=$KIANDA_SUBSCRIPTION_ID"

Token response

A successful response includes the following fields. Additional session metadata is omitted here.

{
  "access_token": "<access-token>",
  "token_type": "bearer",
  "expires_in": 299
}

Use access_token as an opaque credential. expires_in gives its lifetime in seconds; 299 is an example, not a fixed lifetime. Track the returned expiry and obtain a valid token before sending further requests after it expires.

Authenticate API requests

Include the token in the Authorization request header:

Authorization: Bearer <access-token>

Keep credentials and tokens out of source code, URLs, and logs. A token authenticates the user; it does not grant additional permissions.

Continue with the Instances API to work with process documents, or the Summaries API to search data and retrieve aggregates.

Calls from widgets and rules

Calls through Kianda’s client store use the signed-in user’s session. You do not need to request or embed a separate token for those calls. Authentication is still required and is handled by the platform.

Inspect a token for testing

To test an API using your current Kianda session:

  1. Sign in to the target workspace.
  2. Open your browser’s developer tools and select Network.
  3. Reload the page or perform an action that makes an authenticated Kianda API request.
  4. Select the request and find Authorization under Request Headers.
  5. Use the value after Bearer as your access token.

This copies an existing session token. It remains subject to expiry and is intended for temporary testing.

2 - Instances

The Instances API lets you create, retrieve, update and delete process instances.

The Instances API lets you create, retrieve, update and delete Kianda process instances. An instance is an individual process record, such as one incident report or one inspection. A process design defines the forms, fields and rules used by those records.

For integrations that set field values or change form properties, use the mapping-based create and update endpoints. Use the document endpoints when your integration works with a complete Kianda instance JSON document.

Endpoint reference

All paths are relative to your workspace URL.

MethodPathPurpose
POST/api/instances/createCreate an instance from a process design and field mappings.
POST/api/instances/createBulkCreate multiple instances using an array of create requests.
PATCH/api/instances/{name}/updateUpdate an instance using field and form mappings.
PATCH/api/instances/updateBulkUpdate multiple instances using an array of update requests.
GET/api/instances/{name}Get an instance document.
GET/api/instances/{name}/versionGet instance version information.
PUT/api/instances/{name}Update using an instance document.
POST/api/instancesSubmit an instance document.
DELETE/api/instances/{name}Delete an instance.
POST/api/instances/bulkdeleteDelete multiple instances.
GET/api/instances/{name}/fieldsGet selected fields from an instance.

Authentication and request format

Send requests to the workspace that contains the target process and instances. Obtain a bearer access token as described in Authentication, and use an account with permission to perform the requested operation.

Include these headers on requests with a JSON body:

Authorization: Bearer YOUR_ACCESS_TOKEN
Accept: application/json
Content-Type: application/json

GET requests and the single-instance DELETE request have no request body; the Content-Type header is unnecessary for those examples.

Run the examples

The cURL examples use Bash-style environment variables and cURL 7.76.0 or later. They include --fail-with-body so HTTP responses with a status of 400 or above produce a non-zero exit status while retaining the response body.

Set these variables before running an example:

export KIANDA_BASE_URL="https://your-workspace.kianda.com"
export KIANDA_ACCESS_TOKEN="YOUR_ACCESS_TOKEN"

Set KIANDA_BASE_URL to your workspace’s base URL, without a trailing slash. Use your workspace’s custom domain if applicable.

Process, instance, form and field identifiers in the examples are illustrative. Replace them with identifiers from your workspace. Example field values must also be valid for the target field and its configuration.

Examples are independent. For operations on existing instances, replace the sample instance name with an actual instance name from your workspace.

Identifiers and property names

IdentifierMeaningExample
ProcessNameThe identifier of a process design, despite the property name.incident-report
{name}The name of an existing process instance, used in the URL.incident-report-42
InstanceNameThe instance name supplied in an update request body.incident-report-42
FieldNameA field’s internal name, unique within the process.description
FormNameA form’s internal unique name.incident-details
CurrentFormNameThe internal name of the form to set as the current workflow form.review

Use internal field and form names when constructing mappings. Display labels and titles may differ from these names. An instance document’s id and name are separate properties; the routes containing {name} use the instance name.

Mapping request properties use the spelling and casing shown in this reference, such as FieldsMappings, FieldName and InstanceName. Instance documents contain properties such as name, forms, value and text.

Field mappings

Both create and update requests use InstanceRequestFieldMapping objects in FieldsMappings.

PropertyJSON typeDescription
FieldNameStringInternal name of the field to target. Corresponds to field.name.
ValueAny JSON valueValue to assign to field.value. Supply the JSON structure expected by the target field.
TextStringText to assign to field.text, for example the display text associated with a selected value.
VisibleBoolean or nulltrue shows the field; false hides it. An omitted or null setting does not request a visibility change.
EnabledBoolean or nulltrue enables the field; false disables it. An omitted or null setting does not request an enabled-state change.

For example, this mapping assigns a location value and display text, and explicitly shows and enables the field:

{
  "FieldName": "location",
  "Value": "dublin-depot",
  "Text": "Dublin depot",
  "Visible": true,
  "Enabled": true
}

Value is represented by JToken in the request model. It can therefore carry a JSON string, number, boolean, object, array or null. The target field determines which of those representations is valid. For example, send a numeric JSON value when the field expects a number.

Value and Text target separate properties. When your change requires both a stored value and corresponding display text, supply both. For updates, include mappings for the fields you intend to target. The nullable behaviour of Visible and Enabled should not be used as a general rule for clearing or preserving Value and Text.

Background execution

Create and update requests support TriggerField and ExecuteInSeries:

PropertyJSON typeDescription
TriggerFieldStringInternal name of the field to schedule as a background task.
ExecuteInSeriesStringAccepts "yes" or "no". Set "yes" to request that tasks created by the trigger field execute one after another. Set "no" when serial execution is not being requested.

For example, a request can include:

{
  "TriggerField": "submit",
  "ExecuteInSeries": "yes"
}

This is a request fragment: include these properties in a create or update body. ExecuteInSeries uses strings; the visibility and enabled properties use JSON booleans.

Background processing is scheduled separately from the API request. Receiving the HTTP response does not establish that the scheduled work has finished. ExecuteInSeries describes execution of the triggered tasks; it does not define the processing order of items in a bulk API request.

Create an instance

POST /api/instances/create

Creates an instance from the process design identified by ProcessName, applying the supplied field mappings. Use this endpoint when you have a process design identifier and values to populate.

Request body

One CreateInstanceRequest object:

PropertyJSON typeDescription
ProcessNameStringIdentifier of the process design from which to create the instance.
FieldsMappingsArray of field mappingsField values, text and presentation properties to apply. See Field mappings.
TriggerFieldStringField to schedule as a background task. See Background execution.
ExecuteInSeriesString"yes" or "no", controlling whether the triggered tasks are requested to execute in series.
StatusString or nullProcess instance status to set. Use null to ignore this setting.

Use the status values supported by the target process. This reference does not define a fixed status enumeration.

Example

curl --fail-with-body --request POST \
  "${KIANDA_BASE_URL}/api/instances/create" \
  --header "Authorization: Bearer ${KIANDA_ACCESS_TOKEN}" \
  --header "Accept: application/json" \
  --header "Content-Type: application/json" \
  --data '{
    "ProcessName": "incident-report",
    "FieldsMappings": [
      {
        "FieldName": "description",
        "Value": "Loose handrail reported at the loading bay.",
        "Text": "Loose handrail reported at the loading bay."
      },
      {
        "FieldName": "location",
        "Value": "dublin-depot",
        "Text": "Dublin depot",
        "Visible": true,
        "Enabled": true
      }
    ],
    "Status": null
  }'

Add TriggerField and ExecuteInSeries when background execution is part of the operation.

Success response

Returns 200 OK with a JSON object:

{
  "success": true,
  "instanceID": "example-created-instance-id"
}
PropertyDescription
successtrue in the successful response.
instanceIDIdentifier returned by the create result’s id property (result.id). The example identifier is illustrative.

Update an instance

PATCH /api/instances/{name}/update

Applies field and form mappings to an existing instance. It can also set the process status, select the current workflow form and schedule a trigger field.

Path parameter

ParameterTypeDescription
nameStringName of the instance to update.

Request body

One UpdateInstanceRequest object:

PropertyJSON typeDescription
InstanceNameStringName of the instance to update. Use the same instance name as the URL.
FieldsMappingsArray of field mappingsField changes to apply. Uses the same mapping model as create.
TriggerFieldStringField to schedule as a background task.
ExecuteInSeriesString"yes" or "no" for execution of triggered tasks.
StatusStringProcess instance status to set.
FormMappingsArray of form mappingsForm visibility, enabled-state or status changes. See the model below.
CurrentFormNameStringOptional internal form name to set as the current workflow form.

The request supplies the instance name in both the URL and InstanceName. Keep these values identical.

Form mappings

Each InstanceRequestFormMapping targets one form:

PropertyJSON typeDescription
FormNameStringInternal unique name of the form to target.
VisibleBoolean or nullOptional visibility setting: true shows the form; false hides it.
EnabledBoolean or nullOptional enabled setting: true enables the form; false disables it.
StatusStringOptional status to assign to this form.

Omit or use null for form visibility and enabled settings when you are not requesting a change to those flags. Process status, individual form status and the current workflow form are separate settings.

Example: update a field and select the review form

curl --fail-with-body --request PATCH \
  "${KIANDA_BASE_URL}/api/instances/incident-report-42/update" \
  --header "Authorization: Bearer ${KIANDA_ACCESS_TOKEN}" \
  --header "Accept: application/json" \
  --header "Content-Type: application/json" \
  --data '{
    "InstanceName": "incident-report-42",
    "FieldsMappings": [
      {
        "FieldName": "description",
        "Value": "Loading bay handrail isolated pending repair.",
        "Text": "Loading bay handrail isolated pending repair."
      }
    ],
    "FormMappings": [
      {
        "FormName": "review",
        "Visible": true,
        "Enabled": true
      }
    ],
    "CurrentFormName": "review"
  }'

To set statuses, add the process Status at the top level and the form Status inside the relevant FormMappings item. Use accepted status values for the process and form. Selecting CurrentFormName sets the current workflow form; use TriggerField when you also need to schedule background execution.

Success response

Returns 200 OK with a JSON object:

{
  "success": true,
  "instanceID": "incident-report-42"
}
PropertyDescription
successtrue in the successful response.
instanceIDThe InstanceName supplied in the request body.

Update using an instance document

PUT /api/instances/{name}

Updates an instance using a Kianda instance JSON document as the request body. Use this endpoint when your integration already handles the document structure, including forms and fields. For targeted changes expressed as mappings, use Update an instance.

Request body

The instance JSON document itself. Preserve its structure and properties that your integration is not intentionally changing.

A typical document-editing sequence is:

  1. Retrieve the instance using GET /api/instances/{name}.
  2. Edit the relevant properties in the returned document.
  3. Send the resulting document to PUT /api/instances/{name} for the same instance.

For example, retrieve the current document into instance.json:

curl --fail-with-body --request GET \
  "${KIANDA_BASE_URL}/api/instances/incident-report-42" \
  --header "Authorization: Bearer ${KIANDA_ACCESS_TOKEN}" \
  --header "Accept: application/json" \
  --output instance.json

Check that the request succeeded and the file contains the instance document. After making the intended edits, submit it:

curl --fail-with-body --request PUT \
  "${KIANDA_BASE_URL}/api/instances/incident-report-42" \
  --header "Authorization: Bearer ${KIANDA_ACCESS_TOKEN}" \
  --header "Accept: application/json" \
  --header "Content-Type: application/json" \
  --data-binary @instance.json

Response

The controller returns a JSON document.

Get selected fields

GET /api/instances/{name}/fields

Retrieves selected fields from the instance document. No request body is required.

Parameters

ParameterLocationTypeDescription
namePathStringName of the instance to read.
namesQuery stringStringField selector using internal field names. The action parameter defaults to an empty string when omitted. Specify a field name explicitly for a selective read.

Example: retrieve one field

curl --fail-with-body --get \
  "${KIANDA_BASE_URL}/api/instances/incident-report-42/fields" \
  --header "Authorization: Bearer ${KIANDA_ACCESS_TOKEN}" \
  --header "Accept: application/json" \
  --data-urlencode "names=description"

This example selects the field whose internal name is description. --data-urlencode encodes the query parameter value.

Response

Returns the selected fields from the instance document.

Response handling

Read the HTTP status and response body for each operation. The successful responses for create, createBulk, the mapping-based single update, updateBulk and bulkdelete all use 200 OK.

Parse the body according to the endpoint. The create and update responses documented above are JSON objects; bulkdelete returns the JSON string "Completed" when JSON is requested. Other response formats are described in their endpoint sections. Error status codes and error response schemas are not specified in this reference.

The source of the instanceID response value is endpoint-specific: create returns result.id, while the mapping-based single update returns request.InstanceName. Use the instance name for routes containing {name}; the create return statement alone does not establish whether its returned identifier is interchangeable with that name.

This reference does not specify bulk atomicity, rollback, item ordering, retry deduplication or per-item error reporting. After an uncertain result, establish what was applied before repeating a write or an entire batch.

3 - Summaries API

Search Kianda instance data, build condition groups, retrieve paged lists, and calculate tile and chart aggregates.

The Summaries API searches the indexed properties of Kianda process instances. It is the central data-access API used by list, tile, chart, and filter widgets to retrieve selected fields and calculate aggregates across large collections of instance documents.

A request describes the process scope, conditions, fields, and result type. Kianda applies the current user’s instance permissions and executes the query against an optimized summary index. A successful HTTP response contains a JSON array; the objects in that array depend on the requested action.

ActionUse it toSuccessful result with data
listRetrieve selected properties from matching instances.An array of summary records.
tileCalculate a count, sum, or average.An array containing one aggregate result, with the populated value in properties.value.
chartGroup records by a field and calculate aggregate series.An array containing a grouped result with properties.labels, properties.values1, and, when configured, properties.values2.

Designers normally compose conditions through Kianda’s conditions editor. The JSON examples in this page explain the resulting API contract and can also be used by external integrations. Page widgets use the same query concepts through Kianda’s client store.

1. How instance data becomes searchable

Kianda stores selected representations of instance fields in shallow, highly indexed tables. This allows a query to search, sort, and aggregate field data without loading every complete instance document.

The index uses these representations:

Indexed representationSourcePurpose
shortTextA short text representation from field.text.Text search, displayed values, and alphabetical sorting.
dateValueThe value of a date field, together with applicable internal date properties.Date comparisons and chronological sorting.
numberValueThe value of a number field.Numeric comparisons, sorting, and aggregation.

A summary is a query result over this indexed data. It is not an editable process model, and changing a returned object does not update the underlying instance. Use the instance’s name with the appropriate Instances API operation when you need to work with the document itself.

What is indexed

Fields outside tables are indexed automatically. This includes fields inside panels and dialogs.

DataSearch coverage
Ordinary instance fields outside tablesAutomatically indexed using the applicable text, date, or number representation.
Fields inside panels and dialogsIndexed in the same way as other fields outside tables.
Cells and fields inside tablesTable contents cannot be addressed by a Summaries search.
Custom field widgetsTheir field.text representation is automatically searchable.
Arbitrary properties inside a custom field’s structured valueThese properties are not independently searchable.
Client-calculated list columns such as ___CUSTOM_FIELD13Calculated by the client and deliberately omitted from server results.

When a custom field needs to participate in searches, maintain a useful field.text representation. Storing a nested object in field.value does not automatically make each nested property queryable.

Indexing is asynchronous

After an instance document is updated, a background job updates its searchable field data. This typically completes in less than a second, but it is asynchronous: an immediately repeated query can briefly return the previous indexed values.

Treat a successful instance save and a refreshed summary result as separate events. If a workflow must confirm the saved document immediately, use the instance operation’s result or retrieve the instance; refresh summary-based views after the index catches up.

Permissions apply to records

The endpoint is available to authenticated users, including ordinary users. Instance permissions apply to all three actions, including the records contributing to counts, sums, averages, and charts.

Field visibility inside a document is a presentation setting. It does not provide field-level API security. Use instance permissions to control access to the record.

2. Endpoint and first request

POST https://{workspace-domain}/api/summaries
Authorization: Bearer {access-token}
Content-Type: application/json
Accept: application/json

Use the workspace’s domain and the authenticated user’s bearer token. See Authentication for token acquisition.

The controller accepts a query in the request body:

[HttpPost]
public async Task<IEnumerable<Models.Summary>> Post([FromBody] Models.Query query)

The following request retrieves the first page of action instances, ordered by their custom ID:

{
  "action": "list",
  "info": {
    "process": "action",
    "queryType": "all",
    "page": 0,
    "sortFieldType": "fields/field-textbox",
    "isOData": true
  },
  "orderBy": "processCustomID",
  "orderAscending": false,
  "fields": [
    "__NAME",
    "__STATUS",
    "processCustomID",
    "ACT_TXTSIN_Desc",
    "ACT_DATE_DueDate"
  ],
  "conditions": [],
  "rowLimit": 30
}

Save the JSON as query.json and send it, for example, with curl:

curl --request POST \
  'https://your-workspace.kianda.com/api/summaries' \
  --header "Authorization: Bearer $KIANDA_ACCESS_TOKEN" \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/json' \
  --dump-header response-headers.txt \
  --data-binary @query.json

Set KIANDA_ACCESS_TOKEN to your token before running the command. Replace the process and field names with names present in your workspace. The headers are saved separately because list pagination uses the total-items response header.

For list queries, supply a nonempty fields array. The examples also set the action, page size, relationship filter, and sorting explicitly so their intent is clear.

3. Request reference

Top-level query properties

PropertyJSON typePurpose

7. Prepare date conditions before sending

Kianda prepares date conditions on the client so date selections can use client location awareness together with the workspace’s regional settings.

The helper used by the built-in list widget is:

this.get("ruleEngine").parseDateConditions(conditions);

It is called before the same conditions object is included in the request. Use this side-effect-based calling pattern; the built-in list integration does not use a returned array or await a Promise from this helper.

Relative selections such as “Is Before Today” or “Is This Year” are resolved to explicit UTC boundaries in arg2.date1 and arg2.date2. The posted query can retain its original relative operator name alongside those prepared boundaries.

For example, this condition was prepared for a query on 20 October 2026:

{
  "operator": "isBeforeToday",
  "arg1": {
    "text": "Due date",
    "name": "ACT_DATE_DueDate",
    "type": "field",
    "fieldType": "fields/field-date"
  },
  "arg2": {
    "name": "",
    "date1": "1926-10-20T21:42:28.679Z",
    "date2": "2026-10-19T22:59:59.000Z"
  },
  "group": "and"
}

These are captured example boundaries, not reusable constants for every overdue query. Recompute relative dates before issuing a new request.

A custom integration can copy the serialized settings before resolving dates:

const savedConditions = this.get("widget.settings.conditions") || [];
const conditions = JSON.parse(JSON.stringify(savedConditions));

this.get("ruleEngine").parseDateConditions(conditions);

This fragment assumes the component already has access to the rule engine. The copy is appropriate because serialize=true stores plain objects in settings; resolving dates in the request copy avoids rewriting the persistent configuration.

An external REST client does not have access to the Ember helper. It must prepare explicit UTC date boundaries itself for the intended regional/calendar period. Use isBetweenDates for an explicitly selected range, as demonstrated by the tile example. Avoid hard-coding one UTC offset for all dates, since the relevant offset can vary over the calendar.

8. Pagination and sorting

Pagination uses a response header

List requests use:

  • info.page: the zero-based page index.
  • rowLimit: the requested page size.
  • The total-items response header: the total number of matching items.

The JSON body remains an array of summaries. There is no meta or totalItems object added to the raw REST body.

For the second page of the first-request example, keep its query settings and change:

query.info.page = 1;

Given a parsed totalItems header and a query with an explicit page size:

const pageSize = query.rowLimit === 0 ? 1 : query.rowLimit;
const currentPage = query.info.page;

const pageCount = totalItems === null
  ? null
  : Math.ceil(totalItems / pageSize);

const hasNextPage = totalItems === null
  ? null
  : (currentPage + 1) * pageSize < totalItems;

In this client example, null means the total header was not available; it is not a zero-result count.

For example, a total of 75 items with rowLimit: 30 gives three pages:

info.pageUser-facing pageExpected items, if the matching data stays unchanged
0130
1230
2315

Reset the page to 0 when changing the process scope, conditions, relationship filter, or search text. Refresh the total count with the new results.

Choose the correct sort representation

orderBy identifies the field. orderAscending chooses the direction. info.sortFieldType determines which indexed representation SQL uses.

info.sortFieldTypeSort representation
Omitted, empty, or an ordinary text-field typeAlphabetical sorting by shortText.
DateTimeChronological sorting by the indexed date value.
fields/field-dateChronological sorting by the indexed date value.
NumberNumeric sorting by the indexed number value.
fields/field-numberNumeric sorting by the indexed number value.

For example, the following request fragment selects an ascending numeric sort:

{
  "orderBy": "DATAMS_NUM_EmployeeHours",
  "orderAscending": true,
  "info": {
    "sortFieldType": "fields/field-number"
  }
}

Merge these settings into the complete query; this fragment does not include the remaining request properties.

Without the number type, displayed values such as "10" and "2" are sorted as text. Similarly, sorting formatted display dates alphabetically is different from chronological date sorting.

The built-in list widget obtains the sort type from the selected field’s fieldType or type. Carry that metadata through when users change the sort field.

Handle an absent aggregate

Tile consumers must handle both an empty result array and a returned result with no usable aggregate value. A missing aggregate is different from a numeric zero.

This helper reads the confirmed populated-value shape while retaining an explicit no-value state:

function getTileValue(summaries) {
  const result = summaries && summaries[0];
  const properties = result && result.properties;

  if (!properties ||
      !Object.prototype.hasOwnProperty.call(properties, "value")) {
    return null;
  }

  return properties.value;
}

A legitimate value of 0 is preserved. The caller can display a no-data state for null instead of silently reporting a zero.

The reusable conditions editor is:

serialize=true does not mean the HTTP request should contain a JSON string inside conditions. It means the settings contain plain objects that can be included as an array in the query JSON.

The built-in list refresh flow:

  1. Reads the saved conditions and the selected fields.
  2. Resolves date boundaries using ruleEngine.parseDateConditions(conditions).
  3. Maps the selected fields to their stored names.
  4. Builds the query, including info.process, info.page, and sort metadata.
  5. Calls store.query("summary", query) for instance summary data.

The following fragment shows that query-construction path. It assumes the component has the same widget, fields, rule-engine, and store context as the built-in list integration; it is not a complete page-widget component.

const savedConditions = this.get("widget.settings.conditions") || [];
const conditions = JSON.parse(JSON.stringify(savedConditions));
const fieldNames = this.get("fields").mapBy("name");
const pageSize = Number(this.get("widget.settings.pageSize"));

if (fieldNames.length === 0) {
  throw new Error("Select at least one field for the list query.");
}

if (!Number.isInteger(pageSize) || pageSize < 1) {
  throw new Error("Configure a positive whole-number page size.");
}

this.get("ruleEngine").parseDateConditions(conditions);

const query = {
  action: "list",
  info: {
    process: this.get("widget.settings.processName"),
    id: this.get("widget.id"),
    isListWidget: true,
    queryType: this.get("widget.settings.queryType") || "all",
    page: 0,
    isOData: true
  },
  fields: fieldNames,
  conditions: conditions,
  rowLimit: pageSize,
  preferOnline: true
};

const pending = this.get("store").query("summary", query);

For custom page widgets, use preferOnline: true as shown above and await the returned pending Promise inside an error-handled asynchronous method. This option provides one Promise for the result. The full built-in list implementation can go further by handling cached results, a possible pending.onlinePromise, and subsequent record synchronization. That dual-result path is an advanced client-store behaviour, separate from the raw HTTP response, which contains an array plus the total-items header for lists.

Similarly, data.meta in widget code is client-side metadata. A direct REST consumer should read the HTTP header rather than expect data.meta in the returned JSON.

preferOnline is absent from the server Query model, so the direct REST examples omit it. The separate datasource branch in the full refresh function calls dataService.queryFromWidget; it is not the instance-summary request path described here.

Page filters temporarily merge condition groups marked with filterId into the target widget’s live widget.settings.conditions, then fire its refresh action without arguments or awaiting a Promise. Clone that complete array, retaining the temporary groups, before preparing dates or adding request-specific conditions. Kianda removes a filter’s temporary groups when it is cleared and removes temporary groups before saving the page. See Page widget development for the complete component, refresh coordination, and filter wiring.

13. Call the API from JavaScript

This standalone HTTP helper sends a query, checks for an HTTP error, validates the array response, and reads the optional list count.

async function findSummaries(workspaceUrl, accessToken, query) {
  const endpoint = new URL("/api/summaries", workspaceUrl);

  const response = await fetch(endpoint, {
    method: "POST",
    headers: {
      Authorization: "Bearer " + accessToken,
      "Content-Type": "application/json",
      Accept: "application/json"
    },
    body: JSON.stringify(query)
  });

  const responseText = await response.text();

  if (!response.ok) {
    const error = new Error(
      "Summaries request failed (HTTP " + response.status + ")."
    );
    error.status = response.status;
    error.responseBody = responseText;
    throw error;
  }

  const summaries = JSON.parse(responseText);

  if (!Array.isArray(summaries)) {
    throw new Error("Expected a JSON array from the Summaries API.");
  }

  const totalHeader = response.headers.get("total-items");
  const parsedTotal = totalHeader === null || totalHeader.trim() === ""
    ? NaN
    : Number(totalHeader);

  const totalItems = Number.isSafeInteger(parsedTotal) && parsedTotal >= 0
    ? parsedTotal
    : null;

  return { summaries, totalItems };
}

{ summaries, totalItems } is the helper’s own return value; it is not the server’s JSON envelope. Read summaries according to the requested action. Tile and chart consumers should not depend on a list count header.

The helper preserves a zero count and leaves a missing or invalid count as null. It also retains the actual error response text without assuming a particular HttpError JSON property name.

14. Errors, performance, and troubleshooting

Error handling

On failure, the API returns an HTTP error instead of a successful summary array. Check the HTTP response status before interpreting the body as list or aggregate data.

The failure is logged under support/logs, using the category:

Instance | Summary find(Query)

Use the request’s action, process scope, selected fields, prepared conditions, and error response to investigate the failure. An empty successful query result is different from a failed request; do not convert an HTTP error into an empty list or a zero-valued tile.

Keep queries focused

The summary index is designed for fast searching across large collections, including hundreds of thousands of instance documents. Query cost still depends on the scope, requested properties, conditions, and amount of data returned.

  • Set info.process when the data belongs to one process.
  • Select the fields needed by the view.
  • Use a bounded rowLimit and page through lists.
  • Use a tile or chart action when the required output is an aggregate.
  • Include the correct sort type for numbers and dates.
  • Recompute relative date conditions when refreshing.
  • Account for the short asynchronous indexing interval after a save.

Verify an integration

Start with a known instance and a small field selection. Confirm its name, requested properties, and typed sort order. Then test the next page, an empty list, a populated and empty aggregate, and the relevant date filters.
