Kianda is a low-code development platform designed for web developers who want to create robust business process applications without getting bogged down in complex coding tasks. Because Kianda is built on open web technologies—primarily CSS, JavaScript, and micro-services—you can put your existing skills to work right away. Instead of grappling with proprietary systems, you’ll find familiar tools and frameworks, making it straightforward to build and customize applications to meet your organization’s needs.

Key Technologies Under the Hood

Kianda’s front-end leverages established, open-source tools including Ember.js, Bootstrap, and features like web sockets and AJAX for real-time, responsive interfaces. This front-end stack lets you quickly create modern, dynamic user experiences using the same skills you apply every day in web development.

On the back-end, Kianda’s architecture is powered by scalable micro-services running on top of widely used technologies like .NET and Node.js, ensuring that your applications are both reliable and easy to maintain. By embracing these open standards, Kianda allows you to integrate seamlessly with other systems and tools in your ecosystem.

Ember.js and Handlebars

Kianda’s user interface is built using Ember.js, an open-source JavaScript framework well-known for its convention-over-configuration approach. This means you can write less boilerplate code while still delivering high-quality, maintainable applications. Ember.js works hand-in-hand with the Handlebars templating library. Handlebars makes it simple to bind data to templates, dynamically generate HTML, and reuse common UI patterns.

If you’re already comfortable with JavaScript and modern CSS frameworks, you’ll find working with Ember.js and Handlebars an easy step forward. For more on best practices, see our Ember Inspector guide and explore Ember.js documentation and Handlebars documentation.

Why Choose Low-Code with Kianda?

Low-code development reduces the time and effort needed to build enterprise applications. By using Kianda’s graphical interface and predefined building blocks, you can rapidly assemble process apps that integrate with your company’s workflows. At the same time, Kianda’s openness means you’re never locked in. If a standard component isn’t a perfect fit, you can dive into the code and craft a solution that suits your exact requirements.

Kianda provides a large selection of ready-to-use fields and rules, so non-developers can create forms and workflows without writing code. But when you need something more advanced, Kianda’s low-code approach lets you implement custom logic and UI widgets using the CSS and JavaScript skills you already have.

For example, you might create a new field type that displays images in a custom layout or build a bespoke rule widget for integrating with an external data source. You can also fine-tune list widgets for dashboards or write JavaScript expressions to automate tasks like generating unique IDs or formatting text.

What You Can Do as a Developer

With an administrator role, you have access to Administration functions that let you tailor the platform:

  • Modify the Global JavaScript and Global CSS files to set application-wide styles or logic.
  • Create custom Field, Rule, Dashboard, or data connector widgets to extend the platform’s capabilities.
  • Integrate external data sources and use your own JavaScript expressions in fields, rules, or anywhere rich text is used, like in emails and dashboards.
  • Customize list widgets to display data in dashboards in a way that makes sense for your organization’s metrics and KPIs.
  • Incorporate HTML and custom styling in forms and emails to produce richer user experiences.

These options give you the flexibility to shape Kianda to fit your exact business processes, without leaving the familiar territory of open web development.

Kianda Developer: Your Interface for Custom Widgets

Kianda Developer is a user-friendly interface that lets you build and manage reusable widgets. Instead of starting from scratch, you can focus on your core logic or design. You can create:

  • Field widgets: Custom UI elements that appear on-screen, such as specialized inputs or interactive controls.
  • Rule widgets: Automated logic components that manipulate data, set statuses, or initiate actions.
  • Dashboard widgets: Dynamic visualizations or layouts for presenting information on dashboard pages.

1 - Field widget development

Develop custom Kianda field widgets with four display modes, field data binding, validation, child fields, and asynchronous integrations.

A custom field widget renders and edits data in a Kianda form. It can provide a simple input, manage a structured value such as a location or a collection of uploaded files, or integrate an external control such as a payment element. Its main responsibility is to keep the field model consistent with what the user sees and enters.

This guide builds a complete Reference text field and a complete Geolocation field. It then develops a public-file upload example and explains the component patterns needed for a Stripe integration. Along the way, it covers display modes, change notifications, configuration validation, process APIs, and child fields.

The examples target Kianda’s Ember.js widget environment. They use classic Ember components, Handlebars templates, and native JavaScript Promises.

How a field widget works

A widget has two authoring surfaces:

PartResponsibility
Widget UI — Handlebars (.hbs)Renders the Designer preview, editable field, read-only field, and configuration interface.
Widget Code — JavaScript (.js)Defines the Ember component: properties, computed values, actions, lifecycle behaviour, and integration logic.

Kianda supplies the component with field, the field model being rendered, and displayMode, which selects the appropriate view. The associated process is available through this.get("field.process").

Field widgets and rule widgets share Ember component techniques, but have different runtime responsibilities:

ConcernField widgetRule widget
Main purposeRender and manipulate a field’s data.Perform a business action, then return control to the rule engine.
Runtime behaviourRespond to rendering, input events, and component lifecycle events.Run through execute().
TemplateProvides four field views.Provides the rule’s configuration UI.
Designer configurationfield.settingsrule.settings
Asynchronous workThe component manages its own pending state, errors, and completion.The rule engine waits for the Promise returned by execute().

A field widget does not call process.save() to persist its changes. It updates field data in the current process instance. The process’s Save rule or surrounding save/commit workflow handles persistence. A remote upload or payment may have an immediate external effect, independently of whether the process is subsequently saved.

2. Build a complete Reference text field

This first widget stores the same string in field.text and field.value. Its settings let the designer choose a placeholder. It demonstrates the complete path from user input to field data and attached rules.

Widget UI

Paste this complete template into Widget UI:

{{#if (eq this.displayMode "design")}}
  <input
    type="text"
    class="form-control"
    aria-label={{this.field.title}}
    placeholder={{this.field.settings.placeholder}}
    disabled>
{{/if}}

{{#if (eq this.displayMode "edit")}}
  <input
    type="text"
    class="form-control"
    aria-label={{this.field.title}}
    value={{this.field.text}}
    placeholder={{this.field.settings.placeholder}}
    required={{this.field.required}}
    onchange={{action "updateText"}}>
{{/if}}

{{#if (eq this.displayMode "display")}}
  {{#if this.field.text}}
    <span>{{this.field.text}}</span>
  {{else}}
    <span class="text-muted">No reference entered.</span>
  {{/if}}
{{/if}}

{{#if (eq this.displayMode "settings")}}
  <div class="form-group">
    <label for={{concat this.elementId "-placeholder"}}>Placeholder</label>
    {{input
      id=(concat this.elementId "-placeholder")
      type="text"
      class="form-control"
      value=this.field.settings.placeholder}}
    <p class="help-block">A hint shown when the input is empty.</p>
  </div>
{{/if}}

The eq helper comes from the available ember-truth-helpers addon. Each branch uses one of Kianda’s exact mode strings. The Designer preview is a disabled input; the read-only view displays the stored text.

Widget Code

Paste this complete module into Widget Code:

import Ember from "ember";

export default Ember.Component.extend({
  settings() {
    const field = this.get("field");

    if (field.get("settings.placeholder") === undefined) {
      field.set("settings.placeholder", "Enter a reference");
    }
  },

  actions: {
    updateText(event) {
      if (this.get("displayMode") !== "edit" ||
          this.get("field.enabled") === false ||
          this.get("field.visible") === false) {
        return;
      }

      const field = this.get("field");
      const value = event.target.value;

      field.set("text", value);
      field.set("value", value);
    }
  }
});

The native change event passes its event object to the action. Reading event.target.value makes the input source explicit. For this text input, the change is committed when the user finishes editing and leaves the input. If you choose oninput instead, updates occur while typing and can run attached rules on every keystroke.

The order of the setters is deliberate: set the readable text first, then set the value. Kianda observes field.value to trigger the field’s rules, so those rules should see the corresponding text when they run. Replacing the top-level value already provides the notification; there is no additional notifyPropertyChange() call here.

settings() supplies a Designer default only when the property is absent. An intentionally empty placeholder survives reopening the configuration. It does not initialize or overwrite the user’s runtime value.

Try the complete widget

  1. Click Update, add the field to a test process, and open its settings.
  2. Change the placeholder, save the field configuration, and save the process design.
  3. Preview the process. Enter a reference and leave the input. Inspect the field: both text and value should contain the entered string.
  4. Attach a simple rule to the field and verify that committing an edit triggers it.
  5. Make the field required. Clear the input and verify that the normal submission workflow detects the missing value.
  6. Disable the field through Designer or a rule. It should render its stored text through the display branch.
  7. Save the process instance through its normal workflow, reopen it, and confirm that the value is retained.

3. Understand the field model

The widget operates on an Ember Data field model. You do not need to reproduce the model definition in your widget. These are the properties most relevant to authors:

PropertyMeaning and intended use
field.nameThe field’s name, used when resolving fields within a process.
field.titleIts user-facing title.
field.typeIts internal control/widget type.
field.textA readable string representation of the field’s data; defaults to "".
field.valueThe underlying value. It can hold a simple value, an object, or an array.
field.settingsDesigner configuration. A separate empty object is created automatically for each field model.
field.help, field.showTitleHelp text and title-display metadata. showTitle defaults to true.
field.visibleWhether the field is rendered in the form. Defaults to true.
field.enabledWhether it is editable. false makes Kianda render it in display mode. Defaults to true.
field.requiredWhether the commit workflow must reject a missing field value/text. Defaults to false.
field.fieldsChild field models owned by this control.
field.parentFieldIts parent field, when nested inside another control.

field.class, field.customCssClassStyling metadata available on the model.

Typical widgets respect visible, enabled, and required. Designers choose their initial values; specialized rules can change them during execution. Do not repurpose these flags as component-local loading or error state.

Decide what belongs in the model

Use the field attributes for data that should be part of the process:

  • A reference field can use the same string for text and value.
  • A location field can store coordinates in value and a formatted coordinate string in text.
  • An upload field can store file references in value and filenames in text.
  • A compound control can own real child models through fields.

Use component properties such as isBusy, errorMessage, or selectedTab for temporary UI state. Keep browser objects, DOM nodes, upload File objects, service instances, and SDK instances on the component. Store serializable results in the field model.

Keep Designer choices in field.settings. The model already initializes this object; assigning a new empty settings object during rendering would discard saved configuration. The property field.settings and the component method settings() are different things: one holds data, and the other is a convenience hook for the configuration UI.

Rendering, rule notification, and saving

These are related but separate behaviours:

UpdateRendering/data trackingAttached rules
Replace field.value through field.set("value", nextValue)The new value is tracked.A changed value triggers the field’s rules.
Change only field.textThe text is tracked.A custom widget must also notify value if this edit should trigger its rules.
Modify a property inside the existing field.value objectUse Ember-aware setters to update bindings. The data remains part of the field value.Explicitly notify value after the logical update.
Modify the existing field.value arrayUse Ember-aware collection changes to update bindings. The data remains tracked.Explicitly notify value after the logical update.

None of these operations saves the process instance by itself.

A custom field that intentionally stores its data only as text can notify the observed property explicitly:

field.set("text", nextText);
field.notifyPropertyChange("value");

Kianda’s process.setField() does this internally for built-in text-only controls when appropriate. Directly setting a custom widget’s field.text does not gain that behaviour automatically.

Treat a notification as a deliberate point at which attached rules can run. Finish the associated text and data updates first. Avoid adding an extra notification after a top-level value replacement, and avoid initialization code that rewrites the field value on every render.

4. Render the four modes and use lifecycle hooks

this.get("displayMode") is always available on the field component.

Mode stringWhere it is usedWhat to render
"design"The Designer canvas.A useful preview or description of the control.
"edit"An editable field in a running form.Inputs and actions that manipulate the field’s data.
"display"A read-only field, including a disabled field.A readable representation of stored data.
"settings"The field’s configuration interface in Designer.Controls bound to field.settings.

Keep active uploads, payment controls, location acquisition, and other user operations in the editable view. The Designer preview should help a designer understand the widget without initiating those operations.

Kianda’s convenience hooks

On component insertion, Kianda invokes the convenience method for the current mode if you have defined it:

MethodInvocation
edit()On insertion when displayMode === "edit".
display()On insertion when displayMode === "display".
settings()On insertion when displayMode === "settings".

There is no design() convenience method. Render the design view through the template and use normal Ember lifecycle techniques when additional behaviour is needed.

These methods are insertion conveniences, not a promise-based execution pipeline. Kianda does not await Promises returned by field mode hooks. Declaring async edit() does not pause rendering, submission, or the rule engine. Start asynchronous work with explicit error handling and represent pending state in the component.

Do not assume that a convenience method will run whenever displayMode changes. If a long-lived resource must stop when a field becomes read-only, respond to that change explicitly and also clean it up when the component is destroyed. The Geolocation example demonstrates this.

Normal Ember hooks remain available

Use init() for per-instance component setup, such as allocating an array or initializing integration state. Call this._super(...arguments) when overriding an inherited lifecycle hook.

Mount a library that needs a DOM container after insertion, through edit() or an appropriate didInsertElement() implementation. init() runs before the DOM is available. If you override didInsertElement(), retain the superclass call; do not also invoke the same mode method manually and initialize the control twice.

Use willDestroyElement() to release DOM-related resources, listeners, watches, and timers. Match model-event subscriptions with cleanup as well, as shown in the next section. Ember’s component lifecycle documentation explains insertion and destruction hooks.

Native browser and external-library callbacks should enter Ember’s run loop before changing bound state. Use Ember.run(() => { ... }), and check that the component still exists and belongs to the intended field before applying a delayed result. See the Ember 2.18 run-loop guide.

5. Validate configuration and runtime input

Configuration validation and runtime missing-input validation serve different purposes. A valid Designer configuration does not establish that a user has entered a valid runtime result.

Required settings controls

Use required=true on Ember inputs or platform pickers when a Designer setting is mandatory. Native HTML inputs can use required="required" for the same required-input check.

For example, a control that copies file details into two utility fields could use this settings fragment:

{{#if (eq this.displayMode "settings")}}
  <div class="form-group">
    <label>Filename field</label>
    {{field-picker
      process=this.field.process
      required=true
      allowText=false
      selectForms=false
      selectFields=true
      value=this.field.settings.filenameField}}
  </div>

  <div class="form-group {{this.mappingErrorClass}}">
    <label>File URL field</label>
    {{field-picker
      process=this.field.process
      required=true
      allowText=false
      selectForms=false
      selectFields=true
      value=this.field.settings.fileUrlField}}
  </div>
{{/if}}

The required pickers prevent saving configuration with missing selections. For a relationship between settings, such as requiring two different destination fields, subscribe to the field model’s saving event.

Custom configuration checks with saving

The event receives the same validation argument contract used for custom rules:

  • Set args.isError = true to reject the configuration save.
  • Append a clear message to args.errors.
  • Preserve errors already added by other validators.

The following component methods implement the additional check for the settings fragment above. Merge them into that widget’s component; retain any other initialization already performed by its settings() method.

import Ember from "ember";

export default Ember.Component.extend({
  mappingErrorClass: "",

  settings() {
    this._detachSettingsValidation();
    this.set("mappingErrorClass", "");
    this._settingsField = this.get("field");
    this._settingsField.on("saving", this, this._validateSettings);
  },

  _validateSettings(args) {
    const field = this._settingsField;
    const filenameRef = field.get("settings.filenameField");
    const urlRef = field.get("settings.fileUrlField");
    let message = null;

    if (!filenameRef || !urlRef ||
        filenameRef.type !== "field" || urlRef.type !== "field" ||
        !filenameRef.name || !urlRef.name) {
      message = "Select a filename field and a file URL field.";
    } else if (filenameRef.name === urlRef.name) {
      message = "Filename and file URL must use different fields.";
    } else if (filenameRef.name === field.get("name") ||
               urlRef.name === field.get("name")) {
      message = "Choose utility fields other than this upload field.";
    }

    this.set("mappingErrorClass", message ? "has-error" : "");

    if (message) {
      args.isError = true;
      args.errors.push(message);
    }
  },

  _detachSettingsValidation() {
    if (this._settingsField) {
      this._settingsField.off("saving", this, this._validateSettings);
      this._settingsField = null;
    }
  },

  willDestroy() {
    this._detachSettingsValidation();
    this._super(...arguments);
  }
});

Using a stable function reference makes it possible to remove exactly the listener this component added. Detaching before registering also prevents duplicated validation if settings initialization repeats. This follows Ember’s Evented on/off contract.

Perform these checks synchronously. Do not assume that the saving event waits for asynchronous validation. If configuration needs remote information, load it in the settings UI beforehand and validate the resulting state when saving.

Runtime required fields

During submission, Kianda uses field.required and the contents of field.text/field.value to determine whether required input is missing. A custom control must populate these attributes with meaningful data for the commit workflow to work correctly.

Keep pending and error messages in component properties. Storing "Uploading..." or "Location permission denied" in field.text can leave a nonempty field even though the requested input was never obtained. Clearing a value should also clear any text that would falsely suggest the field still has a result.

A nonempty object can still be incomplete for your business purpose. For example, a payment reference with a pending status is not proof of a successful payment. Use Validate input and appropriate conditions for this kind of pre-validation before dependent actions run.

A component-local isBusy, hasErrors, or errorMessage flag does not automatically block the process’s submission workflow. If an operation must finish before submission, make that requirement explicit in process data and validation rules. Decide whether a previous valid result remains acceptable while a replacement is being acquired.

6. Work with structured values and child fields

Replace a structured value

Replacing the top-level value is often the clearest way to publish a complete logical update. This example assumes uploaded contains a validated upload result:

const previousFiles = field.get("value") || [];
const nextFiles = previousFiles.concat([{
  filename: uploaded.filename,
  fileUrl: uploaded.fileUrl
}]);

field.set("text", nextFiles.map(file => file.filename).join(", "));
field.set("value", nextFiles);

This widget’s value contract is an array. Validate or migrate older values if an existing widget previously used a different shape. The new array reference supplies the top-level change notification.

Mutate an existing value

If you keep the same object or array, make Ember-aware changes and explicitly notify value after finishing. For an already initialized file-reference array:

const files = Ember.A(field.get("value"));

files.pushObject({
  filename: uploaded.filename,
  fileUrl: uploaded.fileUrl
});

field.set("text", files.map(file => file.filename).join(", "));
field.notifyPropertyChange("value");

For an existing object, use Ember.set(object, "property", newValue) for observed nested properties, then update any summary text and call field.notifyPropertyChange("value") once the logical change is ready.

Kianda’s built-in file-upload control uses this notification pattern for its array of file references. Nested changes remain tracked as data; the explicit notification is needed to tell the rule engine that the containing field’s logical value changed.

Do not call both replacement and explicit notification for the same update. Also review rules that write to their own triggering field: a value change can trigger another execution and create a loop. Updating several related fields is not an atomic transaction; rules on each field may observe intermediate state.

Use real child field models when needed

An object property inside field.value is different from a child field model. Use child models when the pieces of a compound control need their own field identities, metadata, or rules.

The parent field’s relationship is fields. Its inverse on each child is parentField. Do not invent a subFields relationship on the field model; a table-row helper with that name is a separate structure.

The following method can be added to a parent component that injects the store service. It returns an existing longitude child or creates it once:

import Ember from "ember";

export default Ember.Component.extend({
  store: Ember.inject.service("store"),

  async ensureLongitudeField() {
    const parent = this.get("field");
    const children = await parent.get("fields");

    if (this.isDestroying || this.isDestroyed ||
        this.get("field") !== parent) {
      return;
    }

    const childName = parent.get("name") + "_longitude";
    let child = children.findBy("name", childName);

    if (!child) {
      child = this.get("store").createRecord("field", {
        title: "Longitude",
        name: childName,
        type: "fields/field-textbox",
        settings: {}
      });

      children.addObject(child);
    }

    return child;
  }
});

Call this from the parent control’s deliberate initialization flow, and await it within that flow. Handle errors there. Do not create children unconditionally on every render or while merely displaying an existing value. The parent and derived child names must remain unique in the process design.

Adding the child through fields uses the model’s inverse relationship. Do not call child.save() or process.save() from this initialization. The normal design or instance save workflow handles persistence.

An alternative is to have the designer select existing utility fields with field-picker. This is useful when those fields already participate in process rules or reporting. The parent then updates the selected models through the process APIs.

7. Resolve the process and referenced fields

Access the wrapping process from the field:

const process = await this.get("field.process");

if (!process) {
  throw new Error("The field's process is not available.");
}

This fragment belongs inside an asynchronous method. The property is normally already resolved, but it can require awaiting at the time of access. await works for either case. Do not copy ad hoc .content unwrapping into every widget; the field model already resolves the wrapping process in its computed property.

Field references from the settings UI

field-picker stores a reference, not the live Ember Data field model. A reference usually includes name, text, type, and fieldType. The reference’s text is its selection label; use the process APIs to read the field’s current data.

With allowText=true, a picker can also contain a literal reference such as { text: "Site", type: "text" }. A destination picker should use allowText=false because a destination must resolve to a real field.

APIPurpose
process.findFieldByName(name)Resolve a field by its process name.
process.findFieldByRef(fieldRef)Resolve a field reference; returns the model or undefined.
process.getFieldRefText(fieldRef)Read current field text or literal text; can return undefined.
process.setField(field, value, text)Update a field using the platform API. The text argument is optional.

Use a model’s get("value") or get("text") to read its current attributes after resolving it. Check for a missing reference or removed field before accessing it.

For example, this method fragment updates the destination chosen in field.settings.destination. The calling action should await it and handle any error:

async function writeDestination(component, value, text) {
  const ownerField = component.get("field");
  const process = await ownerField.get("process");
  const reference = ownerField.get("settings.destination");

  if (component.isDestroying || component.isDestroyed ||
      component.get("field") !== ownerField ||
      component.get("displayMode") !== "edit" ||
      ownerField.get("enabled") === false ||
      ownerField.get("visible") === false) {
    return;
  }

  if (!process || !reference || reference.type !== "field") {
    throw new Error("Choose a destination field.");
  }

  const destination = process.findFieldByRef(reference);

  if (!destination || destination === ownerField) {
    throw new Error("Choose an existing destination other than this field.");
  }

  await process.setField(destination, value, text);
}

process.setField() triggers rules associated with the affected field. It can return a Promise when, for example, a data-source-backed list or user picker must finish resolving data. Await it whenever subsequent work depends on completion.

Awaiting this API within your own action sequences that action’s work. It does not make Kianda await the entire field component or automatically delay process submission.

Widget Code

import Ember from "ember";

export default Ember.Component.extend({
  isBusy: false,
  isWatching: false,
  errorMessage: null,
  _watchId: null,
  _requestId: 0,

  settings() {
    const field = this.get("field");

    if (field.get("settings.watchPosition") === undefined) {
      field.set("settings.watchPosition", "no");
    }
  },

  _isEditable() {
    return !this.isDestroying && !this.isDestroyed &&
      this.get("displayMode") === "edit" &&
      this.get("field.enabled") !== false &&
      this.get("field.visible") !== false;
  },

  _accepts(requestId, field) {
    return this._isEditable() && this._requestId === requestId &&
      this.get("field") === field;
  },

  _stopLocation() {
    this._requestId += 1;

    if (this._watchId !== null) {
      navigator.geolocation.clearWatch(this._watchId);
      this._watchId = null;
    }

    if (!this.isDestroying && !this.isDestroyed) {
      this.setProperties({ isBusy: false, isWatching: false });
    }
  },

  stopWhenContextChanges: Ember.observer(
    "displayMode", "field", "field.enabled", "field.visible", function () {
      this._stopLocation();
    }
  ),

  willDestroyElement() {
    this._stopLocation();
    this._super(...arguments);
  },

  actions: {
    capture() {
      if (!this._isEditable()) {
        return;
      }

      this._stopLocation();
      this.set("errorMessage", null);

      if (typeof navigator === "undefined" || !navigator.geolocation) {
        this.set("errorMessage", "Geolocation is not available in this browser.");
        return;
      }

      const requestId = this._requestId;
      const field = this.get("field");
      const watch = field.get("settings.watchPosition") === "yes";
      this.setProperties({ isBusy: true, isWatching: watch });

      const success = position => Ember.run(() => {
        if (!this._accepts(requestId, field)) {
          return;
        }

        const coords = position.coords;
        const value = {
          latitude: coords.latitude,
          longitude: coords.longitude,
          accuracy: coords.accuracy
        };

        this.setProperties({ isBusy: false, errorMessage: null });
        field.set("text", value.latitude + ", " + value.longitude);
        field.set("value", value);
      });

      const failure = error => Ember.run(() => {
        if (!this._accepts(requestId, field)) {
          return;
        }

        this._stopLocation();
        this.set("errorMessage", error.message || "Unable to retrieve your location.");
      });

      const options = {
        enableHighAccuracy: true,
        timeout: 15000,
        maximumAge: 0
      };

      try {
        if (watch) {
          this._watchId = navigator.geolocation.watchPosition(success, failure, options);
        } else {
          navigator.geolocation.getCurrentPosition(success, failure, options);
        }
      } catch (error) {
        failure(error);
      }
    },

    stop() {
      this._stopLocation();
    }
  }
});

Why the example manages callbacks explicitly

The browser can return a position after the user has moved to another form or after a rule has disabled the field. _accepts() checks the request number, the current field model, editability, and component lifetime before allowing a result to update data.

Stopping or replacing a request increments _requestId, so an older callback is ignored. For a watch, the code also calls clearWatch(). Checking the identifier against null is deliberate: a valid identifier of 0 must still be cleared. A single-position request has no equivalent cancellation method here; its late result is simply ignored.

The context observer stops location work when the field or display context changes. Destruction performs the same cleanup. This does not depend on edit() or display() being called again on a mode transition.

In the success callback, component-local state is updated before writing field.value. A rule triggered by the value change may immediately hide or otherwise remove the field, so there is no subsequent component update that assumes the control is still rendered.

Each accepted browser reading replaces the structured value and can trigger attached rules. Watch mode uses one acquisition path rather than starting both a single request and a watch. If the process only needs a final location, leave watching off. Add sampling or meaningful-change thresholds when continuous updates would trigger more work than the workflow needs.

An error remains in errorMessage; it never becomes the field’s coordinate data. The example retains the last successful location if a later attempt fails. If the process requires a fresh capture for each submission, model and validate that requirement explicitly, for example by storing and checking an acquisition timestamp in an extended value contract.

Test this widget

Test acquisition, denied permission, unavailable location, and a timeout. Verify that Designer preview and read-only display do not request location. Enable watching, then stop it, disable the field, and leave the form. In each case, later callbacks should leave the model unchanged. Finally, test two instances on the same form and check that they do not share watch state.

Widget Code

import Ember from "ember";

export default Ember.Component.extend({
  store: Ember.inject.service("store"),
  isBusy: false,
  errorMessage: null,
  _requestId: 0,

  settings() {
    const field = this.get("field");

    if (field.get("settings.accept") === undefined) {
      field.set("settings.accept", ".pdf");
    }
  },

  _isEditable() {
    return !this.isDestroying && !this.isDestroyed &&
      this.get("displayMode") === "edit" &&
      this.get("field.enabled") !== false &&
      this.get("field.visible") !== false;
  },

  _accepts(requestId, field) {
    return this._isEditable() && this._requestId === requestId &&
      this.get("field") === field;
  },

  _invalidateUpload() {
    this._requestId += 1;

    if (!this.isDestroying && !this.isDestroyed) {
      this.set("isBusy", false);
    }
  },

  invalidateWhenContextChanges: Ember.observer(
    "displayMode", "field", "field.enabled", "field.visible", function () {
      this._invalidateUpload();
    }
  ),

  willDestroyElement() {
    this._invalidateUpload();
    this._super(...arguments);
  },

  async _uploadPublicFile(file, folderPath) {
    const adapter = this.get("store").adapterFor("application");
    const session = this.get("store.session");
    const headers = new Headers();

    // This integration uses the sample's synchronous authorization callback.
    session.authorize(adapter.get("authorizer"), (name, value) => {
      headers.append(name, value);
    });

    const url = adapter.buildURL() +
      "/kianda-files/file?isPublic=true&folderPath=" +
      encodeURIComponent(folderPath) + "&name=" + encodeURIComponent(file.name);

    const data = new FormData();
    data.append("file", file);

    const response = await fetch(url, {
      method: "POST",
      headers: headers,
      body: data
    });

    if (!response.ok) {
      throw new Error("Upload failed (HTTP " + response.status + ").");
    }

    const result = await response.json();
    const uploaded = result && result.files && result.files[0];

    if (!result || result.success !== true || !uploaded ||
        typeof uploaded.name !== "string" || !uploaded.name ||
        typeof uploaded.path !== "string" || !uploaded.path) {
      throw new Error("The upload service did not return a valid file reference.");
    }

    return { filename: uploaded.name, fileUrl: uploaded.path };
  },

  actions: {
    async upload(event) {
      const input = event.target;
      const file = input.files && input.files[0];

      // Keep the File object, but allow the same file to be selected for a retry.
      input.value = "";

      if (!file || !this._isEditable() || this.get("isBusy")) {
        return;
      }

      const field = this.get("field");
      const folderPath = String(field.get("settings.folderPath") || "").trim();

      if (!folderPath) {
        this.set("errorMessage", "Configure an existing public folder first.");
        return;
      }

      const requestId = ++this._requestId;
      this.setProperties({ isBusy: true, errorMessage: null });

      try {
        const uploaded = await this._uploadPublicFile(file, folderPath);

        Ember.run(() => {
          if (!this._accepts(requestId, field)) {
            return;
          }

          this.setProperties({ isBusy: false, errorMessage: null });
          field.set("text", uploaded.filename);
          field.set("value", uploaded);
        });
      } catch (error) {
        Ember.run(() => {
          if (!this._accepts(requestId, field)) {
            return;
          }

          this.setProperties({
            isBusy: false,
            errorMessage: error.message || "The file could not be uploaded."
          });
        });
      }
    }
  }
});

The authorization callback above follows the source widget’s session integration. If your session API supplies authorization asynchronously, obtain and await that authorization before starting fetch().

The helper checks both HTTP status and the application response. fetch() does not reject simply because a server returns an HTTP error. When sending FormData, let the browser generate the multipart Content-Type boundary rather than setting that header yourself. These behaviours are covered in the Fetch guide and FormData guide.

If your widget also creates folders, validate the file selection and configuration before making that request, encode folder parameters, and check the folder operation’s application result before uploading. Define how your endpoint treats an already-existing folder instead of assuming every folder response indicates success.

Coordinate upload results with the process

The component only publishes a completed file reference. During the request, loading and failure state stay local. A failed replacement leaves the previous successful upload in the field. If the workflow requires the replacement to finish, add explicit validation for that requirement; isBusy alone does not prevent submission.

The request counter prevents a late result from being applied after the field becomes read-only, is replaced, or is destroyed. It does not cancel or reverse an upload already accepted by the service. A process save also does not wait for this component’s request merely because its action is asynchronous.

To mirror the result into utility fields, add field-picker settings such as those in section 5, resolve the references through field.process, and await each process.setField() call. Validate both destinations before starting the upload. Perform any required copies before publishing the uploader’s final field.value if its attached rules depend on those copies.

Each target update can run that target’s rules. There is no atomic update across the upload service, the utility fields, and the uploader. Handle partial completion in the surrounding workflow when those operations must stay coordinated.

10. Integrate an external control: the Stripe example

This case study draws on an existing Kianda widget named stripe-card. Its Designer settings identify customer and pricing fields, injected services communicate with a connector, and an external SDK renders into the component’s DOM. The relevant architecture and lessons are described below; the original payment implementation is not needed to follow them.

A payment implementation also has its own backend and SDK contract. The example’s connector operations, payment protocol, and legacy confirmation flow should be reviewed as an application integration. They are not additional Kianda field lifecycle hooks.

Give each view a clear purpose

ModeSuggested payment-widget behaviour
designShow a payment-control preview without loading a live payment form.
settingsSelect the connector and required customer, price, and quantity references.
editInitialize and mount the payment control, handle user actions, and publish meaningful results.
displayPresent the stored payment reference and status without accepting new card input.

Initialize, mount, and clean up deliberately

Use these steps for an SDK-backed field:

  1. Resolve configuration and services. Validate required field references and load the integration configuration. Inject services through Ember.inject.service(...) where needed.
  2. Load the SDK once through a shared loader. Cache an in-flight load Promise so multiple instances do not independently repeat script loading. Handle load failure and define retry behaviour.
  3. Wait until the component has a DOM container. Start editable initialization from edit() or the appropriate insertion hook. Do not mount an external element inside async init().
  4. Recheck the context after asynchronous work. The component must still exist, refer to the same field, and be editable before mounting or applying a result.
  5. Scope DOM access to the component. For example, resolve a .payment-container beneath this.element. Do not rely on one global ID shared by multiple field instances.
  6. Release the external control and listeners. Tear down when leaving the relevant mode and on destruction. If the component later becomes editable again, initialize a fresh external control as needed.

For Stripe, load Stripe.js directly from Stripe as described in its current integration guide. Its mount() method accepts a DOM container, and destroy() disposes of an Element. A destroyed Element cannot be remounted.

Kianda does not await the field’s initialization hook. The component must catch initialization errors, show a loading/error state, and prevent its own payment action until its dependencies are ready. Component readiness is separate from process submission validation.

Keep payment data and field state consistent

An external Element does not automatically synchronize its state into the Kianda model. Translate an appropriate integration result into field.text and field.value using the same notification rules as every other custom field.

Keep card-entry data in Stripe’s hosted control. Store suitable references and status information in the process, and keep secret-key operations in the backend. A label such as "Payment successful" in the browser is not the authority for fulfillment: use server-confirmed payment state and the integration’s webhook workflow. Stripe’s payment-status guidance explains how to respond to confirmed outcomes even when the customer leaves the page.

If you store an in-progress payment reference, configure business validation against the required status. A nonempty object alone can satisfy a missing-input check while the payment still needs action.

Review the legacy example before adopting its payment flow

Several implementation details in the earlier stripe-card pattern need deliberate treatment:

  • Initialization must exclude Designer preview. Skipping only settings and display still allows work in design mode. Check explicitly for edit.
  • A command string in field.value is an application convention. A value such as "start_payment" triggers the normal field-value observer and also occupies persisted business data. Prefer an explicit component action for a user operation. If an application retains a command convention, coordinate consumption, rule triggering, and validation explicitly.
  • Sequence asynchronous stages through methods you can await. Do not assume dispatching an action through this.send(...) makes the surrounding flow wait for payment completion. Catch errors where the component owns the operation.
  • Use the confirmation flow for the chosen Stripe integration. Do not copy the legacy confirmPaymentIntent(...) call or replace its name without reviewing the backend protocol. Stripe’s current documentation distinguishes integration-specific flows; its card PaymentIntent confirmation reference describes one such path.
  • Prefer the SDK’s supported authentication handling. A hand-built iframe/modal flow adds lifecycle and message-handling obligations. If an integration genuinely needs postMessage, verify the sender’s origin and source, validate the payload, and remove the listener during teardown. See the browser messaging reference.

This case study explains the field-component responsibilities. A deployable payment flow additionally needs the matching connector/backend implementation and verification against the Stripe API version and integration being used.

2 - Rule widget development

Build custom Kianda rule widgets with a settings UI, validation, asynchronous execution, field updates, and debugging.

A custom rule widget implements a reusable business action in Kianda. It can transform field values, update process data, copy table rows, or call a service. Process designers configure the action and attach it to a process, form, or field using the rule designer.

This guide shows how to build a complete Format text rule, add configuration validation, and develop an asynchronous Generate custom ID rule. It also explains the runtime context, field APIs, reusable UI components, and patterns needed for more advanced rules.

The examples target Kianda’s Ember.js widget environment and use classic Ember components, Handlebars, and native JavaScript Promises.

How a rule widget works

A rule widget has two parts:

PartPurposeWhen it is used
Widget UI — Handlebars (.hbs)Renders the controls a designer uses to configure the rule.When editing the rule in Designer.
Widget Code — JavaScript (.js)Defines an Ember component with configuration behaviour and an execute() method.During configuration, and when the rule engine runs the action.

At design time, Kianda can render the complete component and its template. You can use Ember properties, computed properties, actions, lifecycle hooks, and other components to build the settings interface.

At runtime, Kianda resolves and instantiates the component class, supplies its execution context, and calls execute(). It does not render the rule’s Handlebars template. The action runs, completes, and returns control to the rule engine.

This is the main distinction from a field widget: a field widget provides a control that is rendered in a form; a rule widget performs an action. A rule may update a field that is already rendered, but its own template is the rule’s configuration interface.

Execution and persistence

Keep these behaviours in mind throughout development:

  • execute() is the only runtime entry point. It may be synchronous or asynchronous. The engine waits for a returned Promise to settle. Prefer async execute() for work that may be asynchronous.
  • Return values are ignored. Returning false, an object, or a calculated value does not communicate a result or stop the rule sequence. Write business results into the appropriate process, form, or field model.
  • Process changes are normally saved by a Save rule. A custom rule usually modifies the current process instance. It does not need to save the instance itself. An external API call can have its own immediate side effects, independently of a later process save.
  • Errors do not stop subsequent rules. If execution throws or its returned Promise rejects, Kianda logs the error, records it on the rule, and displays it to the end user in an interactive session. The engine then continues execution. Configure conditions on later rules when they depend on this action succeeding.

1. Create a rule widget

You need access to Administration > Developer, normally through an Administrator or Developer role. You should be familiar with JavaScript and HTML; the examples introduce the Ember and Handlebars conventions they use.

  1. Open Administration > Developer.
  2. Click New widget.

  4. Select Rule as the widget type and confirm the dialog.

Widget Code

Paste this complete module into Widget Code:

import Ember from "ember";

export default Ember.Component.extend({
  settings() {
    const rule = this.get("rule");

    if (rule.get("settings.caseMode") === undefined) {
      rule.set("settings.caseMode", "preserve");
    }
  },

  async execute() {
    const process = this.get("process");
    const rule = this.get("rule");
    const sourceRef = rule.get("settings.source");
    const destinationRef = rule.get("settings.destination");
    const caseMode = rule.get("settings.caseMode") || "preserve";

    if (!sourceRef ||
        (sourceRef.type !== "field" && sourceRef.type !== "text")) {
      throw new Error("Format text: select a source field or enter text.");
    }

    if (!destinationRef || destinationRef.type !== "field") {
      throw new Error("Format text: select a destination field.");
    }

    const destination = process.findFieldByRef(destinationRef);

    if (!destination) {
      throw new Error("Format text: the destination field no longer exists.");
    }

    if (sourceRef.type === "field" &&
        sourceRef.name === destinationRef.name) {
      throw new Error("Format text: source and destination must be different.");
    }

    const sourceText = process.getFieldRefText(sourceRef);

    if (sourceText === undefined || sourceText === null) {
      throw new Error("Format text: the source text could not be read.");
    }

    if (caseMode !== "preserve" && caseMode !== "upper") {
      throw new Error("Format text: the configured letter case is invalid.");
    }

    let result = String(sourceText).trim();

    if (caseMode === "upper") {
      result = result.toUpperCase();
    }

    await process.setField(destination, result);
  }
});

Why the example uses async

process.setField() can return a Promise when the destination needs to resolve data, such as a list connected to a data source or a user picker. Awaiting the call keeps this rule’s completion tied to the field update. await also accepts a synchronous result, so the same pattern works for ordinary text fields.

The settings() method only supplies an editing default. The runtime also has a fallback for caseMode, because execute() must work from the saved configuration without relying on the settings UI having run in the runtime component.

Required inputs and the saving event

Inputs and field pickers with required=true prevent an incomplete rule configuration from being saved. Use the rule model’s saving event for checks that involve multiple settings or business rules, such as requiring different source and destination fields or at least one key column.

When the designer saves the rule configuration, the handler receives an argument object. To reject that save:

  1. Set args.isError = true.
  2. Append a useful message to args.errors.
  3. Optionally set component properties that highlight the relevant controls.

Keep this handler synchronous. Preserve errors added by other handlers: do not reset args.isError to false or replace args.errors. This event validates the rule’s configuration in Designer; it is separate from a Save rule that persists a process instance.

Add semantic validation to Format text

The following is an extension to the Format text component, not a separate module. Replace its existing settings() method with the version below and add the other members inside the same Ember.Component.extend({ ... }) object. Keep its execute() method unchanged.

_settingsRule: null,

settings() {
  this._detachSettingsValidation();

  const rule = this.get("rule");

  if (rule.get("settings.caseMode") === undefined) {
    rule.set("settings.caseMode", "preserve");
  }

  this.set("errors", {});
  this._settingsRule = rule;
  rule.on("saving", this, this._validateSettings);
},

_validateSettings(args) {
  const rule = this._settingsRule;
  const source = rule.get("settings.source");
  const destination = rule.get("settings.destination");

  this.set("errors", {});

  if (source && destination &&
      source.type === "field" &&
      source.name === destination.name) {
    this.set("errors.destination", "has-error");
    args.isError = true;
    args.errors.push("Source and destination must be different fields.");
  }
},

_detachSettingsValidation() {
  if (this._settingsRule) {
    this._settingsRule.off("saving", this, this._validateSettings);
    this._settingsRule = null;
  }
},

willDestroy() {
  this._detachSettingsValidation();
  this._super(...arguments);
}

The template already binds errors.destination to the destination control’s wrapper. This handler uses that property to add a has-error class.

The named callback and matching on/off calls avoid accumulating listeners when the settings editor is opened repeatedly. Cleanup remembers the model that received the listener, so it removes the handler from that same model. These subscription methods are documented in the Ember 2.18 Evented API.

Runtime checks are still necessary. A field may have been removed, or an older saved configuration may not contain a setting added in a newer widget version. Designer validation improves configuration quality; it does not replace validation inside execute().

6. Write asynchronous rules

Prefer async execute() and native Promises for asynchronous work. Kianda also supports a non-async execute() that returns a Promise. The important requirement is that all work needed for completion belongs to the returned asynchronous operation.

ImplementationWhat the engine waits for
A synchronous execute() with no asynchronous workThe method to finish.
An async execute() that awaits its workIts returned Promise to settle.
A non-async execute() that returns a PromiseThat returned Promise to settle.
A method that starts a request or callback and neither awaits nor returns its completionThe method can finish while the work is still running.

Avoid introducing RSVP Promises into new widget examples. Native async/await is the recommended authoring pattern. When integrating a callback-based API, adapt its documented completion and error callbacks to a native Promise and await it. Do not assume that declaring the outer method async automatically waits for callbacks started inside it.

Also avoid array.forEach(async function (...) { ... }) for work that must finish before the rule returns. Use a loop with await for sequential work. Parallel operations require deliberate coordination, especially when they change the same process fields or share table row context.

Example: Generate a custom ID

This example generates a value such as INCIDENT_2026_00042. The designer supplies a prefix/namespace and a destination text field. The rule resolves date tags and expressions, requests a counter value for that namespace, pads the numeric suffix to a minimum of five digits, and updates the field.

The example uses Kianda’s kiandaforms/common expression helper and the /api/counter/up endpoint. Those calls provide the counter-specific behaviour; the component structure and asynchronous execution pattern apply to other integrations too.

    Supported date tags: {YYYY}, {YY}, {MM}, {MMM}, {MMMM}.
    Kianda field expressions such as [FieldName] can also be used.

Widget Code

import Ember from "ember";

export default Ember.Component.extend({
  async execute() {
    const process = this.get("process");
    const rule = this.get("rule");
    const destinationRef = rule.get("settings.field");

    if (!destinationRef || destinationRef.type !== "field") {
      throw new Error("Generate custom ID: select a destination field.");
    }

    const destination = process.findFieldByRef(destinationRef);

    if (!destination) {
      throw new Error("Generate custom ID: the destination field was not found.");
    }

    let namespace = rule.get("settings.namespace");

    if (typeof namespace !== "string" || namespace.trim() === "") {
      throw new Error("Generate custom ID: enter an ID prefix.");
    }

    // Use one captured date for every tag in this execution.
    const now = moment();

    namespace = namespace.trim().replace(
      /\{(YYYY|MMMM|MMM|MM|YY)\}/g,
      function (match, token) {
        return now.format(token);
      }
    );

    const common = require("kiandaforms/common").default;
    namespace = common.evaluateExpression(namespace, process, true);

    if (namespace === undefined || namespace === null ||
        String(namespace).trim() === "") {
      throw new Error("Generate custom ID: the prefix resolved to an empty value.");
    }

    namespace = String(namespace).trim();

    let response;

    try {
      // A data object lets jQuery encode the namespace as a query parameter.
      response = await $.getJSON("/api/counter/up", { namespace: namespace });
    } catch (requestError) {
      const status = requestError && requestError.status;
      const detail = status ? " (HTTP " + status + ")" : "";
      throw new Error("Generate custom ID: the counter request failed" + detail + ".");
    }

    if (!response || response.success !== true ||
        response.value === undefined || response.value === null) {
      throw new Error("Generate custom ID: the counter did not return a value.");
    }

    let suffix = String(response.value);

    if (!/^\d+$/.test(suffix)) {
      throw new Error("Generate custom ID: the counter value is not a non-negative integer.");
    }

    // Five digits is a minimum width; larger values are not truncated.
    while (suffix.length < 5) {
      suffix = "0" + suffix;
    }

    await process.setField(destination, namespace + suffix);
  }
});

This module needs no settings() method because it does not initialise defaults or register custom configuration behaviour. Its required controls provide the initial Designer checks, and execute() validates again before requesting a counter value.

Several implementation details matter:

  • The date replacement is global, so a tag used more than once is replaced throughout the prefix. moment() is captured once, preventing different date lookups within the same execution.
  • [FieldName] expressions are resolved through the Kianda expression helper after the date tags. Do not evaluate a designer’s expression with JavaScript eval().
  • The namespace is passed as request data, so characters such as & and # are encoded instead of altering the query string.
  • HTTP success is distinct from application success. A response with success: false must be treated as a failed operation.
  • The field assignment is awaited as well as the HTTP request.

The date tags use the execution environment’s Moment date and locale settings. If the ID scheme needs a fixed timezone or locale, define that requirement explicitly rather than assuming browser and background-task defaults are identical.

Choose when generation should occur

Configure the rule’s conditions so it generates an ID only when the intended action requires one—for example, when the destination is empty. Repeated execution can request another counter value and overwrite the destination. An empty-field condition helps control normal workflow execution but is not a concurrency guarantee.

A counter request has a server-side effect before the process instance is saved. A later failure, cancelled form, or repeated request can consume a value without retaining the generated ID. This widget does not promise gapless numbering, exactly-once allocation, or automatic rollback of counter values.

For a test run, configure INCIDENT_{YYYY}_, select a text destination, and execute the rule from a separate button. Verify the date prefix, numeric suffix, and subsequent persistence through the normal process save. The suffix depends on the namespace’s current counter state, so it need not start at 00001.

Error handling and dependent rules

Throw an Error with a useful message when the rule cannot perform its action. If you catch an error to add context, rethrow when the operation should still be reported as failed. A catch block that only logs and then returns makes the executor appear to have completed successfully.

Kianda captures execution failures in the event logs and rule.settings.lastError. Successful execution records rule.settings.lastExecuted. In an interactive session, an execution error is also shown to the end user.

The engine continues to subsequent rules after a failure. Neither throw nor return false cancels the overall sequence. Where later actions depend on success, design explicit conditions around the result or a dedicated outcome field. If you use an outcome field, reset it at the beginning of each attempt and set it to success only after all required work completes; otherwise a previous successful value may incorrectly allow later actions.

Also account for partial changes: if an action updates two fields and fails while updating a third, throwing an error does not imply that the first two updates or an external API operation were rolled back. Decide how later Save rules and other business actions should handle that state.

8. Develop table-processing rules carefully

A rule such as Copy unique rows combines several techniques: source and destination table pickers, a conditions editor, input/output mapping, mode selection, and repeatable key-column settings.

Its Designer UI can use rules/rule-conditions to edit a filter and input-mapping to configure column mappings. These components prepare configuration; the runtime code still needs to evaluate conditions and apply the mappings.

For example, the conditions editor can bind a serialised filter to the rule:

{{rules/rule-conditions
  btnText="Copy row conditions"
  leftUseList=true
  leftNodeList=rule.settings.tableFrom.rows
  conditions=rule.settings.filter
  process=process
  serialize=true}}

This is an advanced component configuration using the table selection’s design metadata. Resolve the selected table model for runtime work rather than treating that metadata as the runtime table’s data rows.

Define the copy modes

ModeIntended behaviour
All rowsAdd a destination row for every qualifying source row.
Unique rowsAdd a row only when no destination row matches its configured key columns.
Merge rowsUpdate a matching destination row; create a new row when there is no match.

The table model exposes rows, createRow(), and each row’s subFields for this kind of operation. A destination cell can be resolved from subFields and updated with await process.setField(cell, value, text).

The difficult part is maintaining the execution context and a well-defined matching policy:

  1. Validate before changing rows. Check both tables, every source/destination mapping, the selected mode, and the key references. Reject the same table as source and destination for a copying operation that appends rows: iterating a live source array while appending to it can keep extending the loop.
  2. Require keys for unique and merge modes. A comparison over an empty key list can incorrectly consider every row a match. Each key must refer to a valid destination column that the rule can compare against a mapped source value.
  3. Define equality for the chosen field types. Strict equality between array or object values compares identity, not their contents. Decide which scalar identifiers or normalised values constitute a duplicate.
  4. Keep row-dependent work sequential. Field-name resolution can depend on process.rowContext. Set the appropriate context for each row and await its condition evaluation and field writes before moving to the next row. Do not run these operations concurrently against shared row context.
  5. Restore context in a finally block. Capture the previous rowContext, isInRowContext, and secondaryRowContext, then restore all three values even if a condition, mapping, or field update throws. Setting secondary context to null is not equivalent to restoring a previously existing context.
  6. Include callbacks in execution completion. If condition evaluation uses a callback, make sure its completion is awaited or returned. An asynchronous outer method cannot detect an unawaited callback’s completion by itself.

These requirements also apply to rules that iterate table rows for validation, aggregation, or synchronisation. Test first with simple scalar key columns, then add specialised field types deliberately.

willDestroyElement()Clean up integrations tied to the rendered DOM element.
willDestroy()Release subscriptions to other objects and other instance resources. Call the inherited implementation.
actions and computed propertiesImplement interactive settings behaviour and derived UI state.
execute()Perform the runtime business action using the supplied context and saved configuration.

Mutable component state should be initialised per instance rather than as a shared array or object on the component definition. For example:

init() {
  this._super(...arguments);
  this.set("errors", {});
  this.set("availableOptions", Ember.A());
}

Keep external requests and business mutations out of init() and rendering hooks unless they are specifically required for configuration. Component creation alone should not perform the action that belongs in execute().

See the Ember 2.18 component lifecycle and CoreObject lifecycle API for the underlying hook behaviour.

Service injection

Rules can inject available Ember services such as the store and process engine. These are component-property declarations to add when needed:

store: Ember.inject.service(),
processEngine: Ember.inject.service("process-engine")

Access an injected service with this.get("store") or this.get("processEngine"). The active ruleEngine is already supplied in the runtime context; do not replace it merely because an older example also declares a service injection with that name.

Only use methods supported by the particular service. A service’s availability does not establish an API contract for every internal method. The Ember services guide explains the injection mechanism.

When integrating non-Ember asynchronous callbacks that directly mutate Ember state, also consider Ember’s run loop. This is separate from returning a Promise that tells Kianda when the rule has finished; it does not change the recommendation to use native Promises and the platform field APIs.

10. Support browser and background execution

Custom rules can run both in the browser and in scheduled tasks. Business logic intended for background execution must complete without user interaction.

  • Do not open dialogs or wait for user input in background rules. A dialog can cause the scheduled execution to time out.
  • Obtain input from the supplied process and rule settings. Do not depend on values held only by an open settings editor or a visible form control.
  • Await requests and field updates, and report failures through the normal execution error path.
  • Treat API-side changes and saved process data as separate effects. Decide what should happen if the task is repeated or fails partway through.

The Format text and Generate custom ID examples read configuration and update process data without rendering their own UI. Test the intended rule in a scheduled task as well as an interactive process before relying on background operation, including its service access and failure path.

Use the Schedule a rule documentation to configure the surrounding scheduled workflow.

11. Compile, debug, and maintain the widget

What Update does

When you click Update in Developer, Kianda precompiles the widget with Babel and generates a JavaScript source map (.map) that is made available under public files. The source map helps browser developer tools relate compiled JavaScript to the authored source.

Keep these operations distinct:

OperationWhat you are changing
Update the widget in DeveloperThe reusable component’s implementation and compiled assets.
Save a rule’s configuration in DesignerSettings for that particular use of the widget.
Save/publish the process designThe surrounding process definition, rule attachment, order, and conditions.
Execute the process’s Save rulePersist changes to the running process instance.

After updating code, refresh the test page and verify that it loads the intended compiled asset before diagnosing a result. Use the normal process save/publish workflow when changing its definition. The compilation step alone does not describe cache invalidation, version pinning, or propagation to already open processes; verify the deployed behaviour when planning a change used by existing processes.

Keep settings compatible when maintaining a reusable widget. Adding a default for a missing setting is usually easier to manage than renaming or removing a setting used by existing rule configurations. If a configuration change is necessary, handle that change explicitly and retest representative existing rules.

Debug a custom rule

  1. Reproduce in a test process. Trigger the rule from a known attachment point with a small, predictable input.
  2. Inspect the supplied models. Use browser developer tools or Ember Inspector to check rule.settings, resolved fields, and the relevant process state.
  3. Set a breakpoint in execute(). Use the generated source map, or temporarily add a debugger; statement to the source. A breakpoint in didInsertElement() will not diagnose runtime execution that does not render the component.
  4. Follow asynchronous work. Inspect the Network panel and confirm that requests and field assignments are awaited before later rules execute.
  5. Check the recorded outcome. Review event logs, settings.lastError, and settings.lastExecuted, together with the current rule input. Do not infer current success from an old diagnostic alone.
  6. Verify persistence separately. A visible field change and a saved process instance are different checks. Run the normal Save rule and reopen the instance when validating persistence.

Kianda also provides a Rule debugger for stepping through rules and Rule diagnostics for investigating process instances. See Custom widget debugging for browser debugging techniques.

Here’s a more detailed example of a global function that updates a dashboard header based on a user’s selection in a dropdown:

function setHeader(elementId) {

    if (headerElement) {
      headerElement.innerHTML = selectedText;
    }
  });
}

How This Helps:

What is a PWA?

A Progressive Web Application (PWA) is a web-based application that delivers a native app-like experience on any device—mobile, tablet, or desktop—without requiring an app store download. PWAs leverage modern web technologies to offer features such as offline availability, push notifications, and fast load times, all while maintaining the convenience and accessibility of a standard website.

By running Kianda as a PWA, you gain a flexible, secure, and user-friendly solution for enterprise mobility without the overhead of traditional mobile app distribution. Accessing Kianda through a PWA feels like using a native app, but with the continuous updates and centralized maintenance of a cloud-based web application.

  • No App Store Submission:
    Distribute and update your enterprise application directly. Users can “install” Kianda from their browser without going through an app store.

  • Offline Capability:
    Work seamlessly—even without network access. Tasks, forms, and process instances can be completed offline and automatically synced when connectivity returns.

Easy Installation and Maintenance

Installing Kianda as a PWA is as simple as adding it to your home screen. Since updates happen behind the scenes over the web, there’s no need for users to download updates manually. Your IT team can roll out new features or fixes instantly, ensuring everyone is always on the latest version.

8 - Webhooks

Learn how to configure webhooks to receive web callbacks from record creation

Webhooks in Kianda provide a straightforward way to notify external applications in real time when certain events occur within your workspace. Rather than constantly polling Kianda for updates, webhooks allow you to react immediately whenever process instances are created, updated, or deleted. This makes event handling efficient and responsive.

When a webhook event fires, Kianda sends an HTTP GET request to the configured URL(s), passing along essential details such as the process name, instance ID, and the type of event. Your external application can then use this information to update its own records, trigger workflows, or perform any other actions needed.

Note: The callback request has a timeout of 10 seconds. If your external service does not respond within this time, the request may fail.

Setting Up Webhooks in Kianda

To implement webhooks, you need an Administrator or Developer role. For more details on roles, see Users & Groups.

  1. Open the Developer Resources:

    • Go to Administration in the left-hand sidebar.
    • Click on Developer to open the Developer resources page.

  2. Access Webhooks:

    • Click on Webhooks to configure callback URLs.

  3. Configure Instance Callback URLs:

    • The Instance Callback URLs dialog box appears.

  4. Enable and Specify Callbacks: Turn on the relevant callback(s) using the sliders, then provide the URL(s) that Kianda should call when the selected event occurs.

    • Created Callback: Fires whenever a new process instance is created.

      • Kianda sends a HTTP GET request with parameters:
        instanceID={instanceID}&processName={processName}&eventType=created

    • Updated Callback: Fires whenever a process instance is updated.

      • Kianda sends a HTTP GET request with parameters:
        instanceID={instanceID}&processName={processName}&eventType=updated

    • Deleted Callback: Fires whenever a process instance is deleted.

      • Kianda sends a HTTP GET request with parameters:
        instanceID={instanceID}&processName={processName}&eventType=deleted

    For each event type, you can enter one or more URLs (one URL per line) to notify multiple services simultaneously.

  5. Help and Guidance: If you need more details, click the Help button to see additional instructions and examples.

  6. Save Your Settings:

    • Click OK to confirm your settings.
    • Click Close if you want to exit without saving.

Once configured, Kianda will send HTTP GET requests to the specified URLs whenever the corresponding event occurs. You can then build logic in your external application(s) to handle these events—updating records, triggering other workflows, or integrating with third-party services.

In summary, Kianda’s webhook functionality allows your workspace to seamlessly connect with external applications in real time, reducing the need for constant polling and making it easier to maintain synchronized data and processes across systems.

9 - Introduction to Ember.js in Kianda

Learn about the emberjs in Kianda

Kianda’s front-end is built on Ember.js, a framework designed for creating rich, interactive web applications. Ember provides a powerful structure for building interfaces that dynamically respond to user input and data changes. To produce its UI, Ember uses Handlebars, a templating language that makes it easy to bind data models to your HTML.

If you’re familiar with modern web development, you’ll find Ember’s approach intuitive: templates, components, and data binding come together to create a smooth, dynamic user experience within Kianda’s low-code environment.

Handlebars: Templating Made Easy

Handlebars is a templating language that lets you write declarative HTML with embedded expressions. These expressions—enclosed in {{double curly braces}}—are automatically replaced by values from your data models.

For example:

<p>{{firstname}} {{surname}}</p>

If the data model provides:

{
  firstname: "Ryan",
  surname: "B'Oul"
}

The rendered HTML is:

<p>Ryan B'Oul</p>

This simple approach makes it easy to display dynamic data without writing complex logic. When data updates, the template refreshes automatically, ensuring users always see the latest state.

Using Properties and Dot Notation

Handlebars supports “dot notation” to access nested properties in objects:

<p>{{person.firstname}} {{person.surname}}</p>

If person is an object with firstname and surname properties, Handlebars will replace them in the template, keeping your markup clean and readable.

Built-in Helpers

Ember and Handlebars include helpers—functions used inside templates to handle common tasks. For example, each lets you iterate over arrays:

<ul>
  {{#each employee as |name|}}
    <li>{{name}}</li>
  {{/each}}
</ul>

Given:

{
  employee: ["Ryan B'Oul", "Mike Balcoome", "Maddie Lehane"]
}

The template renders:

<ul>
  <li>Ryan B'Oul</li>
  <li>Mike Balcoome</li>
  <li>Maddie Lehane</li>
</ul>

Similarly, if conditions let you show or hide content based on data:

{{#if manager}}
  <h1>{{firstname}} {{lastname}}</h1>
{{/if}}

If manager is true, the heading appears; if not, it’s hidden. Helpers let you add simple logic to templates without cluttering your code.

Creating Custom Helpers

You can extend Ember’s capabilities by writing your own helpers. For instance, you might create a helper to format dates or combine multiple properties. This keeps your templates clean and your logic reusable.

Inspecting the App with Ember Inspector

To better understand Kianda’s components and data, you can use the Ember Inspector—a browser add-on that helps you explore the internal structure of Ember apps. With it, you can:

  • Inspect components and their properties.
  • Understand the data models and routes.
  • See which templates are used for specific UI elements.

How to Get Started with Ember Inspector:

  1. Install the Ember Inspector from the Chrome Web Store or your browser’s add-ons marketplace.
  2. Open your Kianda workspace and log in.
  3. Right-click on the page and select Inspect.
  4. Navigate to the Ember tab in the developer tools.
  5. Explore components, routes, and data to learn how Kianda’s UI is constructed.

Components and Properties

In Kianda, many UI elements—like fields, rules, and dashboard widgets—are implemented as Ember components. By inspecting them with the Ember Inspector, you can discover their properties and understand how they’re rendered. This knowledge can guide you when creating your own custom widgets or applying advanced customizations.

In Summary:
Ember.js and Handlebars provide a robust foundation for Kianda’s dynamic interfaces. Handlebars lets you write simple, declarative templates tied directly to your data, while Ember’s helpers and components help keep your application organized and responsive. Combined with tools like the Ember Inspector, these technologies give you the power to understand and customize Kianda’s front-end to suit your needs.

10.1 - Microservice Creation

What is a Microservice

A microservice is a self contained independent service, usually hosted in the cloud, which can integrate with applications through REST APIs. Microservices allow developers to focus on developing a service without worrying about dependencies.

A microservice can be developed using almost any programming language.

Prerequisites

Before you get started, check that the following prerequisites are in place:

  • Ability/permissions to create resources with a cloud platform, for example, Google Cloud, AWS or Azure
  • Administration role or permissions within an Admin group within Kianda, see Users and Groups for more information
  • Visual Studio installed or other text editor for your chosen programming language

Microservice Requirements

Your microservice should implement the following three functions:

  1. Test
  2. Metadata
  3. Query

It is required that the microservice uses security best practices, to encrypt sensitive data using AES encryption and verify that each request and response is secure using a HMAC signature.

Test

The Test function ensures that the user is authorized to use the datasource. If they are not authorized then this function can be used to authorize the user and retrieve an access token for any further requests.

The steps involved in creating the test function are as follows:

  1. Deserialize the data in the custom connector request - see schema for details and Test sample code.

  2. Decrypt the encrypted settings property bag using the shared secret key and the Decrypt function, see Encryption/Decryption sample code for an example.

  3. Authorize the user and retrieve bearer token for subsequent requests and save the token to the settings property bag.

  4. Add the oauth token to the settings property bag and encrypt using your secret key.

  5. Create custom connector response and include success message to indicate test succeeded/failed.

  6. Sign the response using the EncryptdatawithHMACSHA256 method and include in the custom connector response, see Encryption/Decryption sample code for an example.

To help you get started, see sample code for the Test function by going to Test sample code.

Security

AES256

Advanced Encryption Standard (AES) is the technique used to encrypt sensitive data. This is a symmetric encryption technique, which means the same key is used to encrypt and decrypt the data, it is also a 2-way encryption algorithm.

HMAC

Hash based Message Authentication Code (HMAC) is used to ensure query responses are coming from the correct end point. HMAC is also an encryption algorithm but unlike AES it’s one-way encryption, meaning it isn’t decrypted on the other side. It is used for verification, for example if we encrypt a secret key using HMAC with a request id and then do the same in the response, we can verify that we have got the response back from the correct endpoint and know that it has not been tampered with because both hashes will match. The hash used is SHA256.

With AES we are encrypting and decrypting data and this method is fast and secure for large data, while with HMAC we use it to simultaneously verify both the data integrity and authenticity of a message.

Before you begin

Please note before you begin that there are three key steps that need to be implemented in order to create and use a customised connector.

  1. Microservice - create a microservice that will implement metadata, query and test functions, click on the Microservice link to get further details.

  2. Use Kianda features to create and test your customised connector - use Developer to register a new connector and use Data sources to create a connector datasource for the newly customised connector.

  3. Process - use the custom connector to bring data into a process and use the query hook to filter the data.

Register a new connector

To create a new customised connector, follow the steps below:

  1. From the left-hand side menu, go to Administration > Developer then within the Connectors panel click on New Connector.

  1. In the Create Connector dialog box, add a Title and browse for an Icon URL for your connector. The Connector Unique ID is automatically generated by the system.

  2. Make sure to copy the secret key to a safe location where you will find it as it will be needed later. You can do this by a) clicking on Download TXT which will result in the Secret Key being downloaded as a CSV file or b) clicking on Copy Key to Clipboard, then click on OK when done.

  3. Ensure that this secret key is added to your Microservice code, see Encryption and Decryption sample code, where you need to replace the string in the GetSecretKey function as shown below:

Query Hook

The Query hook allows a query to the datasource to be customised. Parameters are passed into this function to allow customisation to happen. These parameters are: datasource, query, rule and process; sample schemas are available for each at the Sample schema link.

In the sample code below, the filter is obtained by drilling into the query conditions object. This is just one example of how the query can be customized before being processed, which is an advantage of using custom connectors. Take a look at the query schema for more information

 query(datasource, query, rule, process) {
    if(query.conditions)
    {
      query.filter = query.conditions[0].conditions[0].arg2.value;
    }
    return query;
  }

This ties in with the query success hook which handles the result which is returned from the datasource, which can also be customized.

QuerySuccess hook

The idea of the query success hook is to be able to customize the response of a datasource query for example drill into a complicated json response based on a condition.

Encryption and Decryption sample code

        public static string HashWithHMACSHA256(string key, string value)
        {

            using (var hash = new HMACSHA256(Convert.FromBase64String(key)))
            {
                var hashedByte = hash.ComputeHash(Encoding.UTF8.GetBytes(value));
                var hashed = Convert.ToBase64String(hashedByte);
                return hashed;
            }
        }

        public static string AESEncrypt(string key, string plainData, out byte[] iv)
        {
            var _key = Convert.FromBase64String(key);
            using (Aes aes = Aes.Create())
            {
                aes.GenerateIV(); 
                aes.Mode = CipherMode.CBC;
                iv = aes.IV;
                aes.KeySize = 256;
                aes.Key = _key;
                using (var encryptor = aes.CreateEncryptor())
                {
                    using (MemoryStream ms = new MemoryStream())
                    {
                        using (CryptoStream cs = new CryptoStream(ms, encryptor, CryptoStreamMode.Write))
                        {

                            using (StreamWriter sw = new StreamWriter(cs))
                                sw.Write(plainData);
                        }
                        return Convert.ToBase64String(ms.ToArray());
                    }
                }

            }
        }


        public static string AESDecrypt(string key, string encryptedData, byte[] iv)
        {
            var buffer = Convert.FromBase64String(encryptedData);
            var _key = Convert.FromBase64String(key);
            using (Aes aes = Aes.Create())
            {
                aes.KeySize = 256;
                aes.Mode = CipherMode.CBC;
                aes.Key = _key;
                aes.IV = iv;
                using (var decryptor = aes.CreateDecryptor())
                {
                    using (MemoryStream ms = new MemoryStream(buffer))
                    using (CryptoStream cs = new CryptoStream(ms, decryptor, CryptoStreamMode.Read))
                    {
                        using (StreamReader sw = new StreamReader(cs))
                            return sw.ReadToEnd();
                    }
                }
            }

        }

        public static string GenerateAESKey()
        {
            using (Aes aes = Aes.Create())
            {
                aes.KeySize = 256;
                aes.GenerateKey();
                return Convert.ToBase64String(aes.Key);
            }
        }

            resultExc.queryResult.message = "Exception occured; " + ex.Message;
            resultExc.signature = signature;
            return resultExc;
        }

        return result;
    }
